# 코드 컨벤션

이 문서는 Minecraft Fabric 26.3 기반 멀티 개발 협업을 위해 에이전트 코딩과 사람 코딩 모두가 따라야 할 기본 규칙입니다.

## 필수 확인 문서

코드를 수정하기 전에 다음 문서를 확인합니다.

1. [`docs/file-name-conventions.md`](file-name-conventions.md)
2. 수정하려는 기능의 `docs/features/*.md`
3. 관련 기능 패키지와 공통 진입점

기능을 새로 만들거나 기존 기능을 분리할 때는 기능 문서와 파일 이름 규칙도 같은 변경에서 업데이트합니다.

## 프로젝트 구조

- 모드 진입점은 `com.example.myfirstmod.MyFirstMod`로 최소화합니다.
- 기능 구현은 `com.example.myfirstmod.feature.<feature-name>` 패키지에 둡니다.
- 기능 진입 클래스는 `<FeatureName>Feature`로 명명합니다.
- 기능별 상태와 상수는 해당 기능 클래스 또는 기능 패키지 내부에 둡니다.
- 기능 간 공유 로직이 생기기 전에는 패키지를 합치지 않습니다.
- 공통 동작은 근거가 명확한 경우에만 별도 `common` 또는 `util` 패키지로 추출합니다.

권장 구조:

```text
src/main/java/com/example/myfirstmod/
├── MyFirstMod.java
└── feature/
    ├── lightning/
    │   └── LightningStickFeature.java
    ├── zeusleap/
    │   └── ZeusLeapFeature.java
    └── stormsovereign/
        └── StormSovereignFeature.java
```

## 기능 초기화

- 기능을 하나의 명확한 진입점에서 등록합니다.
- 일반적으로 `public static void initialize()` 메서드를 사용합니다.
- Fabric 이벤트 등록은 기능 패키지 내부의 `initialize()` 메서드에만 둡니다.
- `MyFirstMod.onInitialize()`에서는 기능 클래스의 초기화 호출만 수행합니다.
- 기능 초기화 메서드는 여러 번 호출되지 않도록 구성합니다.

```java
public final class ExampleFeature {
	private ExampleFeature() {
	}

	public static void initialize() {
		// Fabric event registration
	}
}
```

## 상태와 동시성

- 서버 틱 관련 상태는 명확한 스레드 안전 범위 안에서 관리합니다.
- 플레이어별 상태는 `UUID` 키를 사용합니다.
- 보스나 엔티티별 상태도 엔티티의 `UUID`를 키로 관리합니다.
- 상태 맵은 항목이 더 이상 유효하지 않을 때 반드시 정리합니다.
- 서버 틱에서 월드 간 상태를 순회할 때는 누수와 중복 처리를 방지합니다.
- 클라이언트 전용 상태와 서버 전용 상태를 혼합하지 않습니다.

예시:

```java
private static final Map<UUID, ExampleState> ACTIVE_STATES = new HashMap<>();
```

## 서버와 클라이언트 경계

- 서버 전용 엔티티 생성, 피해, 소리 재생, 틱 처리는 서버 세계를 사용합니다.
- 아이템 입력 콜백에서 먼저 서버 세계인지 확인합니다.
- 클라이언트 패키지의 코드는 서버 로직을 직접 포함하지 않습니다.
- Fabric 환경 구분이 필요한 경우 명시적인 `level.isClientSide()` 또는 Side 분리 규칙을 사용합니다.
- 공통 타입만 클라이언트와 서버 양쪽에서 사용할 수 있도록 설계합니다.

## 타입과 캐스팅

- 다운캐스트는 안전하게 확인한 뒤 사용합니다.
- `instanceof` 패턴 매칭을 사용하여 불필요한 중복 캐스팅을 줄입니다.
- EntityType 등 레지스트리 결과에 필요한 캐스팅은 기능 구현 인접 위치에 유지합니다.
- 와일드카드나 제네릭 타입을 추측으로 확장하지 않습니다.

## 상수와 매직 넘버

- 반복해서 사용하거나 조정 가능성이 있는 값은 `private static final` 상수로 분리합니다.
- 거리, 시간, 피해, 반경은 단위를 변수명 또는 주석으로 구분합니다.
- 틱 단위 상수는 `_TICKS` 접미사를 사용합니다.
- 거리나 반경은 용도에 맞게 `_RADIUS`, `_DISTANCE` 등의 이름을 사용합니다.

```java
private static final int LEAP_COOLDOWN_TICKS = 100;
private static final double IMPACT_RADIUS = 5.0D;
private static final float IMPACT_DAMAGE = 6.0F;
```

## 메서드와 클래스

- 메서드는 한 가지 책임만 수행하도록 작게 유지합니다.
- 상태 변경 메서드와 계산 메서드를 구분합니다.
- 기능 진입 메서드와 서버 틱 메서드의 역할을 명확히 나눕니다.
- 유틸리티 성격의 클래스는 인스턴스 생성을 막기 위해 `private` 생성자를 둡니다.
- 상태 보관용 작은 내부 클래스는 기능이 소유하는 위치에 둡니다.
- 과도한 중첩과 깊은 조건문을 피하고 조기 반환을 사용합니다.

권장 메서드 흐름:

```text
initialize() -> 이벤트 등록
event callback -> 입력 검증 -> 기능 실행
tick method -> 기존 상태 조회 -> 상태 갱신 -> 정리
```

## Java 포맷과 이름

- 패키지명은 소문자와 점 구분 형식을 사용합니다.
- 클래스는 `UpperCamelCase`를 사용합니다.
- 메서드와 변수는 `lowerCamelCase`를 사용합니다.
- 상수는 `UPPER_SNAKE_CASE`를 사용합니다.
- 탭 들여쓰기와 생략 없는 중괄호를 사용합니다.
- 연속된 공백을 의미 없는 줄로 남기지 않습니다.
- 이름은 실제 역할을 드러내며 모호한 이름을 피합니다.

## 이벤트 콜백

- 콜백은 등록 시점과 실행 시점의 책임을 분리합니다.
- 콜백에서 상태 변경 전에 아이템, Shift 상태, 서버 세계, 플레이어 타입을 검증합니다.
- 검증 실패 시 기본 동작으로 넘길지 성공으로 소비할지 명확하게 반환합니다.
- 서버에서 처리하는 기능은 클라이언트에서 처리하지 않습니다.
- 콜백 내부에 매우 긴 기능 구현을 넣지 말고 별도 메서드로 분리합니다.

## 피해와 엔티티

- 피해 대상을 가져올 때는 생존 여부와 기능 소유자 제외 여부를 확인합니다.
- 거리 계산은 `distanceToSqr` 또는 필요한 상황에 맞는 제곱 거리 계산을 사용합니다.
- 넉백 방향이 0에 가까울 때는 명시적인 기본 방향을 설정합니다.
- 보스나 목표 탐색은 범위를 제한하고 다차원 전역 검색을 피합니다.
- 엔티티 상태 맵은 엔티티 사멸 또는 월드 이탈 시 정리합니다.

## 로깅

- 모드 전반의 로거는 `MyFirstMod.LOGGER`를 사용합니다.
- 기능별 세부 로그가 필요하면 기능 진입점에서 기존 로그 패턴을 재사용합니다.
- 정상 반복 틱에서 과도한 로그를 남기지 않습니다.
- 예외 상황은 필요한 정보와 함께 로그에 남기되 게임 실행을 의도치 않게 중단하지 않습니다.

## 문서화

- 기능 추가나 동작 변경 시 `docs/features/`의 해당 문서를 함께 수정합니다.
- 문서에는 구현 위치, 동작 흐름, 상호작용 아이템, 시간 또는 피해 값을 기록합니다.
- 내부 구현을 그대로 나열하지 말고 다른 개발자와 에이전트가 수정 판단에 필요한 내용을 작성합니다.
- 새로운 기능 문서는 `docs/README.md`에 링크를 추가합니다.
- 이름 규칙 변경은 `docs/file-name-conventions.md`와 이 문서를 함께 갱신합니다.

## 에이전트 코딩 작업 지침

에이전트는 다음 순서로 작업합니다.

1. 변경 범위와 관련 기능 패키지를 확인합니다.
2. 기존 기능 문서와 동일 기능의 상수 및 상태를 읽습니다.
3. 기능별 패키지 밖의 공통 진입점만 최소한으로 수정합니다.
4. 다른 기능의 상태 맵, 이벤트 등록, 틱 메서드를 재사용하거나 변경하지 않습니다.
5. 새 기능을 추가하면 독립 패키지와 독립 Markdown 문서를 함께 생성합니다.
6. 완료 후 관련 기능의 코드와 문서 경로를 확인합니다.

에이전트가 피해야 할 작업:

- 여러 기능의 구현을 다시 `MyFirstMod.java`에 합치기
- 기존 기능의 동작을 확인하지 않은 채 상수와 수치 변경
- 기능 문서 없이 새로운 기능 등록
- 여러 기능이 내부 상태 맵을 공유하도록 연결
- 요청 범위와 무관한 포맷팅 또는 리팩터링
- 기존 문서 파일명을 규칙과 맞지 않게 임의 변경

## 검증

코드 변경 후 최소한 다음을 확인합니다.

```bash
./gradlew build
```

- 컴파일 성공
- 기능 패키지 경로와 클래스 이름 일치
- 기능 문서 링크 유효성
- 기존 기능 이벤트가 중복 등록되지 않았는지 확인
- 서버 틱 상태 맵이 엔티티가 사라질 때 정리되는지 확인
